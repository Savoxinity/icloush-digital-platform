# iCloush智慧工厂——Phase033-登录与权限分层路线图-V3.3.0

## 版本概述

本次 **Phase033** 的目标不是继续堆叠单点页面能力，而是为后续多品牌前台与员工后台的长期运营，先把 **登录方式、会话模型与权限边界** 统一成一套可执行路线图。当前系统已经能够依赖 Manus OAuth 完成登录、写入 `users` 表并通过 `globalRole` 控制 Admin 后台访问，但它仍然是 **单一登录入口、单一身份主键、单一权限抽象** 的模式：前台用户、企业采购用户、后台员工与超级管理员都共用同一条 OAuth 会话链路，无法支撑更符合中国大陆业务场景的手机号验证码、邮箱验证码、微信登录与员工后台账号分层。

因此，Phase033 的核心交付不是立刻替换现有认证系统，而是先完成三件事情：第一，把现有认证与权限现状盘清；第二，确定后续应采用的 **“前台身份体系” 与 “后台员工体系” 双轨结构**；第三，把第一批可落地的数据库字段、服务端接口边界与前端入口拆分方案写清楚，避免后续进入实现阶段时又回到边开发边改模型的低效率状态。

## 当前系统现状

| 维度 | 当前实现 | 当前价值 | 当前缺口 |
| --- | --- | --- | --- |
| 前端登录入口 | `apps/admin/src/const.ts` 与 `apps/web-b2b/src/const.ts` 统一通过 `getLoginUrl()` 生成 OAuth 跳转地址 | 所有站点都能快速接入现成登录 | 不支持手机号验证码、邮箱验证码、微信登录分流，也无法区分前台与后台入口 |
| 服务端登录回调 | `server/_core/oauth.ts` 在 `/api/oauth/callback` 交换 code、同步用户并签发 session cookie | 登录链路简单稳定，便于演示和内部联调 | 登录提供方单一，回写字段仅覆盖 `openId / email / loginMethod / lastSignedIn` 等基础信息 |
| 会话模型 | `server/_core/sdk.ts` 以 `openId + appId + name` 生成 JWT session，并在请求中反查 `users` | 现有 cookie 会话机制足够轻量 | 会话载荷没有区分账号类型、登录渠道、后台员工身份域，也没有多登录源合并策略 |
| 用户主表 | `packages/database/schema.ts` 中 `users` 仅含 `openId / unionId / mobile / email / loginMethod / accountType / globalRole / status` | 已预留手机号、邮箱、账户类型和全局角色基础字段 | 缺少“登录主体”“绑定渠道”“员工目录”“验证码凭证”“微信身份绑定”等结构化模型 |
| 后台权限 | Admin 的 `adminProcedure` 仅判断 `globalRole in ['admin', 'super_admin']` | 规则清晰，适合当前小团队 | 无法表达品牌员工、销售、财务、运营等后台角色的细分授权边界 |
| 前台会员分层 | 主要依赖 `brandMemberships.memberType` 区分 `b2b_customer / b2c_customer / brand_admin / sales / finance / ops` | 已有品牌级业务角色的雏形 | 会员身份与员工身份仍混在同一用户体系中，缺少登录层面的隔离 |

## 目标结构

本轮建议把后续登录体系明确拆成 **两层账号域、三类登录方式、两级权限判断**。

### 1. 两层账号域

前台站点与交易体系应以 **客户身份域** 为核心，服务对象包括散客、企业采购联系人、品牌会员与企业审核申请人。这里最重要的是降低注册和登录门槛，因此应优先支持手机号验证码、邮箱验证码，以及面向中国大陆高频场景的微信登录。后台管理体系则应切换为 **员工身份域**，服务对象包括销售、财务、运营、品牌管理员与平台超级管理员。员工后台不应继续默认复用前台用户的登录态，而应拥有更明确的账号来源、岗位角色、品牌归属与审计记录。

### 2. 三类登录方式

从业务优先级看，建议采用下面的实施顺序：

| 登录方式 | 优先级 | 适用场景 | 说明 |
| --- | --- | --- | --- |
| 手机号验证码 | P0 | 企业采购申请、客户留资、前台会员登录 | 中国大陆用户接受度最高，也是后续销售回访、订单通知与企业线索沉淀的最稳入口 |
| 邮箱验证码 | P1 | 企业采购、海外或非微信场景的补充登录 | 适合作为手机号之外的备用入口，也便于企业客户资料归档 |
| 微信登录 | P1 | 微信内传播、私域转化、品牌 H5 裂变 | 适合 H5 站点传播，但要与手机号绑定策略配合，避免单纯依赖微信身份导致 CRM 联系信息缺失 |
| 现有 OAuth | P2 | 内部协作、迁移过渡、运维兜底 | 不建议直接废弃，可保留为过渡通道和内部测试入口 |

### 3. 两级权限判断

权限不应只依赖一个 `globalRole` 字段，而应拆成：

| 层级 | 建议职责 | 示例 |
| --- | --- | --- |
| 全局权限 | 只描述平台级后台能力 | `super_admin`、`platform_admin` |
| 品牌/组织权限 | 只描述品牌内岗位与数据范围 | `brand_admin`、`sales`、`finance`、`ops`、`procurement_contact` |

这样做的目的，是把“能不能进入后台”与“进入后台后能看哪些品牌、哪些模块、哪些数据”拆开。后续 Admin 里的仪表盘、订单、企业审核与品牌配置，都可以在统一登录后根据品牌组织关系继续细分，而不是继续把所有复杂性挤在 `globalRole` 一个字段里。

## 建议的数据模型增量

本轮不直接落库迁移，但建议下一实施阶段按下面方向扩充数据模型。

| 新模型/字段方向 | 作用 | 首批建议 |
| --- | --- | --- |
| `authIdentities` | 记录用户绑定的登录渠道 | `userId`、`identityType`（mobile/email/wechat/oauth）、`identityValue`、`verifiedAt`、`isPrimary` |
| `authVerifications` | 记录验证码发送与校验状态 | `channel`、`target`、`codeHash`、`expiresAt`、`consumedAt`、`scene` |
| `employeeProfiles` | 把员工后台账号从普通客户资料中分离 | `userId`、`employeeNo`、`department`、`jobTitle`、`employmentStatus` |
| `brandStaffMemberships` 或扩展 `brandMemberships` | 记录员工与品牌的岗位关系 | `brandId`、`userId`、`staffRole`、`scopeJson` |
| `users.loginMethod` 扩展为最近登录方式 | 保留兼容字段 | 允许记录 `mobile_otp`、`email_otp`、`wechat_oauth`、`manus_oauth` |
| `users.accountType` 细化 | 区分客户与员工账号 | 建议从 `personal / enterprise` 扩为 `customer_personal / customer_enterprise / employee / system`，或新增 `accountDomain` 字段 |

## 首批实施抓手

为了让后续实现阶段更可控，建议把第一批工作拆成 **不会破坏现有数据库数据、且能逐步上线** 的三步。

### 步骤一：先保留现有 OAuth，补齐认证抽象层

首先，不要立刻删除现有 OAuth 登录链路，而应在前后端新增一个更抽象的认证入口层。例如前端不再只暴露 `getLoginUrl()`，而是改成 `getAuthEntry({ audience, method, returnPath })` 之类的统一构造器。这样在前台可以弹出“手机号登录 / 邮箱登录 / 微信登录”，后台可以进入“员工登录”入口，而现有 OAuth 先作为 `method = 'legacy_oauth'` 的兼容分支继续使用。

### 步骤二：先让手机号/邮箱验证码成为前台登录主入口

对于 web-b2b 与各品牌 H5 来说，第一批最有价值的并不是先做复杂的微信 UnionID 合并，而是先把 **手机号验证码登录** 做成默认主入口，并允许企业采购场景补充邮箱验证码登录。这样做的业务收益最直接：销售线索、会员识别、订单通知与回访联系都能立刻得到更高质量的联系方式沉淀。

### 步骤三：员工后台从“共享客户身份”切到“员工身份目录”

Admin 后台建议新增“员工登录入口”和“员工身份目录”概念。短期内仍可兼容 OAuth 登录，但登录成功后必须检查：当前用户是否拥有员工身份记录、是否处于有效岗位状态、是否绑定可访问品牌。只有满足这些条件，才允许进入后台主界面；否则只保留前台访问能力，不应把普通客户账号自动视为后台可登录用户。

## 首批接口边界建议

| 端点/模块 | 本轮定义的目标边界 | 下一步实施建议 |
| --- | --- | --- |
| `client/src/const.ts` | 从单一 `getLoginUrl()` 演进为统一登录入口构造器 | 新增 `getAuthEntry`、`getEmployeeLoginEntry`、`getCustomerLoginEntry` |
| `server/_core/oauth.ts` | 保留现有 OAuth 回调，改造为统一认证管道中的一个 provider | 抽出 provider 层接口，允许手机号/邮箱/微信共享登录后写入逻辑 |
| `server/_core/sdk.ts` | 继续承担 session 签发与请求鉴权，但 session payload 需要增加身份域信息 | 在不破坏现有 cookie 的前提下支持 `accountDomain / authMethod / staffRoleVersion` |
| `useAuth()` | 从“未登录即 OAuth 跳转”改为“按 audience 选择登录入口” | 支持 `audience = 'customer' | 'employee'` 与更细分的重定向策略 |
| `adminProcedure` | 从单纯依赖 `globalRole` 升级为“已登录 + 员工身份有效 + 角色可访问资源” | 先加一层 `employeeProcedure`，再逐步替换旧守卫 |

## 风险与约束

本轮路线图特别强调 **兼容迁移**，而不是一次性重写认证系统。原因在于，当前数据库中的用户、企业申请、订单、品牌会员与支付资料都已经开始互相关联，一旦直接推倒重建登录主表，很容易造成历史订单与业务数据脱链。因此，后续改造必须遵循以下原则：

第一，保持 `users.id` 作为业务数据的稳定主键，不做破坏性迁移。第二，新增登录渠道采用“身份绑定表”承载，而不是反复在 `users` 表里塞越来越多的互斥字段。第三，员工后台必须与前台客户身份分层，但不意味着一定要拆成完全不同的用户表，更合理的方式是共享用户主键、拆分身份域与权限关系表。第四，微信登录必须与手机号补全策略绑定，否则会出现“能登录、但无法留资和回访”的业务问题。

## 本轮交付结果

本次 Phase033 已完成的是 **路线图与边界固化**：一方面，明确了当前系统仍然以 Manus OAuth、`openId` 与单一 session cookie 为中心；另一方面，明确了下一阶段要以“客户身份域 + 员工身份域”的双轨结构推进，并把手机号验证码、邮箱验证码、微信登录和员工后台权限分层的实施顺序、数据模型与接口边界写清楚。这样，下一阶段无论是先做手机号验证码登录、先做员工目录，还是先给品牌 H5 增加微信登录入口，都可以在同一架构前提下推进，而不必每次从头讨论模型。

## 下一阶段建议

下一阶段建议按下面顺序进入真正开发：首先完成 `authIdentities` 与 `authVerifications` 的 schema 设计；其次实现前台手机号验证码登录；然后补齐员工身份目录与 `employeeProcedure`；最后再接入微信登录与多渠道账号绑定。这样能够在不打断当前演示链路的前提下，逐步把系统从“可用的 OAuth 原型”升级为“适合中国大陆运营与品牌协同的正式登录体系”。

# iCloush H5 封装微信小程序 WebView 实施清单

## 背景与结论

iCloush 当前的零售前台以 React H5 形态运行，适合继续承担品牌叙事、商品浏览、PDP 说服与订单确认等“内容承载层”。如果要把这套 H5 封装进微信小程序，首先要承认一个核心事实：**小程序里的 WebView 只是网页承载容器，不是微信支付环境本身**。微信官方对 `web-view` 的定义是“小程序内承载网页的容器”，而且非关联公众号网页必须先配置业务域名，个人类型小程序也暂不支持该能力。[1] [2]

对于支付链路，官方小程序支付产品页把标准闭环定义为“用户打开小程序、下单、调用小程序支付 API、输入支付密码、支付完成后返回小程序”。这意味着在 iCloush 的正式方案中，**H5 可以负责下单与参数准备，但微信支付的最终触发应该回到小程序原生页，而不是继续停留在 WebView 内做网页版收银**。[3] 与此相互印证的是，微信开放社区在讨论“小程序内嵌 H5 调微信支付”时，给出的可执行办法也是由 H5 使用 `wx.miniProgram.navigateTo` 跳转到小程序原生支付页，再由原生页调用 `wx.requestPayment` 完成支付。[4]

## 能做什么，不能做什么

| 模块 | 建议定位 | 说明 |
| --- | --- | --- |
| H5 展示层 | 继续复用 | 适合承接首页、品牌馆、货架、PDP、购物袋、订单确认页等高复用页面。 |
| WebView 容器 | 作为流量与内容入口 | 负责把 H5 放进小程序，但不应承担最终支付调用。 |
| 小程序原生页 | 承担支付桥接与结果回传 | 使用原生页面承接 `wx.requestPayment`，并把支付结果回写给 WebView。 |
| 微信支付配置 | 以小程序支付为主线 | AppID 与商户号需要绑定，且主体需一致。[3] |
| H5 内直接走 JSAPI | 不建议作为小程序正式方案 | JSAPI 面向微信内置浏览器场景；小程序 WebView 需要单独走小程序支付桥接。[4] |
| H5 内直接走非微信 H5 支付 | 不适合作为小程序主链路 | H5 支付主要对应非微信浏览器场景，不宜混入小程序 WebView 主流程。[4] |

## 实施前置条件

在进入代码开发前，项目必须先满足域名、主体与账号三个前提。其一，H5 所在域名必须被配置为小程序业务域名；微信官方同时提示，如果页面里还有 iframe，那么 iframe 的域名也需要进入白名单。[1] [2] 其二，业务域名必须使用 HTTPS，且按照微信平台能力要求完成对应主体合规配置；否则即使 H5 本身能在浏览器打开，也无法在小程序 `web-view` 中稳定承载。[1] 其三，小程序支付要求 AppID 与商户号完成绑定，并且主体一致，这一步直接决定后续 `wx.requestPayment` 是否具备可上线的商户身份。[3]

| 前置项 | iCloush 需要确认的内容 | 当前判断 |
| --- | --- | --- |
| 小程序类型 | 是否不是个人类型小程序 | 必须确认，否则 `web-view` 不可用。[2] |
| 业务域名 | 预览域名、正式域名、支付回跳页域名 | 必须逐一登记。[1] |
| HTTPS | H5 域名与所有嵌入资源均为 HTTPS | 必须满足。[1] |
| iframe / 三方嵌入 | 是否存在外部 iframe、视频或三方页面 | 存在则需单独核对白名单。[2] |
| 支付主体 | 小程序 AppID 与微信支付商户号主体是否一致 | 必须一致。[3] |
| 微信支付证书 | 当前商户号、证书序列号、私钥是否配对 | 现阶段仍需继续核对，当前正式支付尚被 SIGN_ERROR 阻塞。 |

## 推荐的技术路线

推荐把现有 React H5 保持为“统一内容层”，同时新增一个极薄的小程序壳层。用户从小程序首页进入某个承载页时，小程序只做两件事：一是把目标 H5 URL 拼成 `web-view` 的 `src`；二是为 H5 提供运行环境识别与支付桥接出口。H5 进入小程序环境后，应首先通过 `wx.miniProgram.getEnv`、`window.__wxjs_environment` 或 userAgent 中的 `miniProgram` 标识识别当前是不是小程序 WebView。[2]

当用户在 H5 中点击“去支付”时，H5 不直接调网页版微信支付，而是先请求 iCloush 服务端生成**小程序支付参数包**。随后，H5 通过 `wx.miniProgram.navigateTo` 跳到小程序原生支付页，将订单号、时间戳、随机串、`package`、签名等参数传过去。[2] [4] 小程序原生支付页在 `onLoad` 中读取这些参数，并调用 `wx.requestPayment`。支付成功或失败后，小程序可通过页面返回、重新拼装 WebView URL 参数，或者结合 `postMessage`/状态页轮询，把结果反馈回 H5 展示层。[2] [4]

## 建议的数据与页面分工

| 层级 | 建议页面/模块 | 责任边界 |
| --- | --- | --- |
| H5 | `/shop`、`/object/:id`、购物袋、订单确认页 | 商品展示、规格选择、订单草稿、支付前确认、品牌内容承载 |
| 服务端 | `createRetailOrder` 后续扩展为小程序支付参数生成 | 生成订单、识别支付环境、返回小程序支付所需参数 |
| 小程序原生页 | `pages/h5pay/index` 或同类桥接页 | 调用 `wx.requestPayment`、承接成功/失败、返回 H5 |
| H5 支付结果页 | 订单结果页或订单详情页 | 读取支付结果、刷新订单状态、展示下一步动作 |

## 对现有 iCloush 代码库的具体改造建议

第一步，应在前台增加**微信环境识别层**。现有 H5 需要有一个统一的 `detectWechatContainer()` 或等效能力，至少区分“普通浏览器”“微信内 H5”“小程序 WebView”三种环境。这样，商城在点击支付时才能正确选择 `sandbox`、未来公众号 JSAPI 或小程序原生支付桥接，而不是把所有微信流量都视作同一支付环境。

第二步，应在服务端支付创建接口里增加**支付场景分发字段**。当前 `paymentMode` 已经预留出 `sandbox / production_ready / production_live` 三态，下一步建议额外引入 `paymentRuntime` 或等价概念，例如 `web_h5`、`wechat_browser_jsapi`、`mini_program_bridge`。这样一来，订单创建逻辑不会把 WebView 场景误导到网页支付实现。

第三步，应新增一个**小程序支付参数接口**。这个接口不负责 H5 直接付款，而是返回小程序原生页可直接喂给 `wx.requestPayment` 的参数集合，并明确带上订单号、品牌标识、回跳页地址与结果校验令牌，避免前端自行拼凑支付参数。

第四步，应设计一条**支付结果回传协议**。微信开放文档说明 `postMessage` 触发时机有限，更适合作为辅助通知，而非唯一的实时支付完成信号。[2] 因此更稳妥的做法是：小程序原生支付页完成支付后先回到 WebView，再由 H5 调自己的订单查询接口确认最终状态；页面参数回写只承担“触发刷新”的作用，不直接视为最终到账凭证。

## 合规与体验风险

| 风险项 | 表现 | 建议应对 |
| --- | --- | --- |
| 业务域名未登记 | WebView 无法打开或白屏 | 先登记正式域名、预发布域名与必要子域名。[1] |
| H5 资源链路不纯 | 页面局部白屏、静态资源失败 | 检查图片、脚本、接口、iframe 是否全部符合 HTTPS/白名单要求。[1] [2] |
| 误用 JSAPI/H5 支付 | 在小程序里支付失败或体验割裂 | 小程序场景统一切原生支付桥接，不与网页支付混用。[3] [4] |
| 支付结果回传过度依赖 URL | 前端展示成功但订单未真正入账 | 以服务端订单状态查询为准，URL 参数仅作提示。 |
| 证书与商户配置不一致 | 正式支付报 401 SIGN_ERROR | 优先核对商户号、证书序列号与私钥配套关系。 |

## 建议的实施顺序

当前最合理的顺序不是立刻写小程序代码，而是先把环境与协议定清楚。第一阶段先完成业务域名、支付主体、证书配对核查，并补一份“小程序支付参数接口”设计稿。第二阶段再在 H5 中加入环境识别和支付运行时分发逻辑，同时落一个最小化的小程序原生支付桥接页。第三阶段才是联调支付成功、取消、失败、返回 H5 后查询订单状态三条主链路。这样能最大限度保护现有数据库与商城业务数据，同时把风险集中在可控的壳层接入与支付桥接层，而不是重写整套 H5。

## 微信支付证书序列号核对建议

考虑到 iCloush 当前已经注入私钥，但正式支付仍返回 `401 SIGN_ERROR`，接下来应把“支付桥接代码开发”和“商户凭据核对”拆成两条线。前者继续按小程序原生支付桥接方案推进；后者单独回到微信支付商户平台，核对当前商户号对应的 API 证书序列号是否与已注入私钥来自同一套证书。只有当商户号、证书序列号、私钥与 AppID 主体全部对齐后，`production_live` 才适合重新打开。

# 微信支付 production_live 阻塞诊断备忘

## 当前结论

本轮已把微信支付阻塞问题从“泛化的签名失败”进一步收敛为**可证伪的运行时诊断结果**。

首先，`apps/web-b2b/server/wechat.key.diagnosis.test.ts` 已新增并执行。该测试证明当前环境变量中的 `WECHAT_PAY_PRIVATE_KEY_PEM` **可以被 Node/OpenSSL 成功解析**，且可以稳定导出 RSA 公钥指纹。这意味着当前问题**不是**最基础的 PEM 文本不可读，也不是“明文私钥完全无法被运行时加载”的类别。

其次，新增诊断同时覆盖了原始 PEM 与换行规范化 PEM 两种路径。结果表明，当前私钥并未落入“原始 PEM 与规范化 PEM 都不可解析”的分支，也未暴露出必须依赖 passphrase 才能解开的显式加密私钥特征。因此，阻塞点已经基本排除为以下几类主因：**纯粹的 PEM 结构损坏、单纯的 `\\n` 转义未还原、明显的加密私钥未解锁**。

但是，商户证书—私钥是否成对这一点，在当前环境里仍未能彻底自动闭环。原因不是测试能力不足，而是**运行环境里没有额外提供商户证书 PEM**。没有商户证书 PEM，就无法把 `WECHAT_PAY_CERT_SERIAL_NO` 与从私钥导出的公钥做最终配对验证。因此，这一步现在已经从“推测性问题”升级为**明确的数据缺口**：要么补入商户证书 PEM 做本地比对，要么回到微信商户平台重新下载并人工核对同一批 API 证书与私钥。

最后，扩展后的 `apps/web-b2b/server/wechat.credentials.test.ts` 已把联通测试前置拆分为本地私钥可用性断言，再去请求 `GET /v3/certificates`。本次复跑时，本地私钥分类断言通过，但联通请求没有返回旧的 `401 SIGN_ERROR`，而是在 TLS 建连前出现 `ECONNRESET`。与此同时，用 `curl -I https://api.mch.weixin.qq.com/v3/certificates` 做最小探测可以收到 `405 Method Not Allowed`，说明沙盒到微信网关的基础网络可达。综合判断，这更像是**Node fetch 在当前时点与微信网关 TLS 握手阶段出现了瞬时连接重置**，而不是域名不可达；不过这并没有推翻原有的密钥配对疑点，只是意味着当前联通测试还受到一层网络抖动噪声影响。

## 本轮自动化诊断结果一览

| 诊断维度 | 结果 | 解释 |
| --- | --- | --- |
| `WECHAT_PAY_PRIVATE_KEY_PEM` 原始/规范化可解析性 | 已通过 | 私钥可被当前 Node/OpenSSL 运行时读取，不属于最基础的 PEM 破损场景 |
| `\\n` 转义导致的解析失败 | 暂未命中 | 本轮未出现“换行规范化前后都失败”或“仅因 `\\n` 未还原而失败”的证据 |
| 显式加密私钥/缺少口令 | 暂未命中 | 未触发 `ENCRYPTED PRIVATE KEY` 导致的解析失败分支 |
| 运行时公钥指纹导出 | 已通过 | 证明可从当前私钥稳定推导出 RSA 公钥 |
| 商户证书-私钥配对自动校验 | 未完成 | 缺少商户证书 PEM，当前只能定位到“尚无法自动证明成对关系” |
| 微信 `/v3/certificates` 联通 | 本轮受 TLS `ECONNRESET` 干扰 | 基础网络可达，但 Node fetch 本次在握手前被重置，需复跑确认是否瞬时网络噪声 |

## 与此前 `SIGN_ERROR` 结论的关系

历史联通结果曾出现 `401 SIGN_ERROR`，并明确指向 `authorization.signature` 的 `sign not match`。该结论仍然具有参考价值，因为本轮新增测试已经把“私钥根本不能解析”的可能性显著缩小。换言之，如果后续网络恢复稳定、联通测试再次回到 `SIGN_ERROR`，那么更高概率的根因就不再是 PEM 解析失败，而是：

1. `WECHAT_PAY_PRIVATE_KEY_PEM` 与 `WECHAT_PAY_CERT_SERIAL_NO` 并非同一张商户 API 证书；
2. 当前环境中的私钥虽然可解析，但内容已经与微信商户平台下载原件不完全一致；
3. 当前使用的是旧序列号，而私钥已轮换。

## 当前可确认的结论边界

现阶段可以确认的是：**问题并不主要停留在“Node 根本读不懂 PEM”这一层**。现阶段仍然不能确认的是：**当前私钥是否与 `WECHAT_PAY_CERT_SERIAL_NO` 对应的商户证书真正成对**。这也是下一步最应优先补齐的证据缺口。

## 下一步建议

### 一、补入商户证书 PEM，完成最后一跳配对校验

建议新增以下任一环境变量，以便让现有诊断测试直接完成证书—私钥自动比对：

- `WECHAT_PAY_MERCHANT_CERT_PEM`
- `WECHAT_PAY_CERT_PEM`
- `WECHAT_PAY_CLIENT_CERT_PEM`

一旦有了商户证书 PEM，现有测试即可同时校验：

1. 证书序列号是否等于 `WECHAT_PAY_CERT_SERIAL_NO`；
2. 证书公钥与当前私钥推导出的公钥是否一致。

### 二、把平台证书自动拉取与缓存实现单列为下一里程碑

`packages/payments/src/index.ts` 目前已把 callback 分支真实切开，但正式回调验签仍依赖：

- 拉取 `/v3/certificates`
- 平台证书缓存与刷新
- 回调头验签
- `resource` 解密

因此，`WECHAT_PAY_PLATFORM_CERT_PEM` 的自动拉取/动态刷新仍应作为支付正式接入前的基础设施任务继续推进。

### 三、对微信网关联通测试执行二次复跑，隔离网络噪声

由于本轮联通测试出现 TLS `ECONNRESET`，建议在后续继续复跑一次 `wechat.credentials.test.ts`。如果二次复跑重新回到 `401 SIGN_ERROR`，就可进一步坐实“密钥与证书序列号不匹配”而不是网络问题；如果持续出现 TLS 握手前重置，则需要额外评估当前沙盒出网到微信支付网关的稳定性。
